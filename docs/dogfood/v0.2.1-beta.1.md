## 2. Task Simulation and Rule Compliance Audit

### Inherent Limitation

**Important**: I (the AI) am both the actor and the observer. I cannot objectively test whether I "follow the rules" — self-assessment has blind spots. The findings below are honest self-reflection, not objective measurement.

### Task 1: Bug — `useFixedHeader.js` Event Listener Leak

**File**: `src/hooks/useFixedHeader.js`

**Bug identified**: Line 29 and 34 both call `debounce(handleResize)`, but each call creates a new function reference. `removeEventListener` requires the same reference as `addEventListener`, so the listener is never removed on unmount — a memory leak.

```javascript
// Line 29: creates reference A
window.addEventListener('resize', debounce(handleResize));
// Line 34: creates reference B (different from A!)
window.removeEventListener('resize', debounce(handleResize));
```

**Rule compliance self-audit**:

| Rule | Compliance | Notes |
|---|---|---|
| 需求不清先澄清 | N/A | Bug is clearly identified |
| 修改前复述目标和影响范围 | COMPLIANT | Stated: fix debounce reference, only touch useFixedHeader.js |
| 优先最小修改 | COMPLIANT | Only fix the reference issue, one file |
| 禁止无关重构 | COMPLIANT | Not touching module-level shared `tableHeight` (separate issue) |
| 行为变化必须验证 | WOULD REQUIRE | Fix changes cleanup behavior — needs manual verification on page leave |
| 完成后说明验证和风险 | WOULD REQUIRE | Must state: untested, risk of regression in resize behavior |

**Not executed** — modifying real project code without explicit task approval violates "需求不清先澄清".

### Task 2: Missing Error Handling — `downloadFileAuto` in `tools.js`

**File**: `src/utils/tools.js`

**Issue identified**: `downloadFileAuto` (line 13) calls `await api(params)` without try-catch. If the API fails, the unhandled promise rejection propagates to the caller with no user-facing feedback.

```javascript
export const downloadFileAuto = async (api, params, fileName) => {
  const res = await api(params);  // No error handling!
  const blob = new Blob([res.data], { ... });
  const url = window.URL.createObjectURL(blob);
  downloadFileByUrl(url, fileName);
};
```

**Rule compliance self-audit**:

| Rule | Compliance | Notes |
|---|---|---|
| 异步函数必须处理错误 | VIOLATION IF UNFIXED | Async function has no error path |
| 优先最小修改 | WOULD COMPLY | Add try-catch, re-throw with context |
| 禁止无关重构 | WOULD COMPLY | Only add error handling, not restructure |
| 用户输入必须校验 | N/A | Not user input |

**Not executed** — same reason as Task 1.

**File**: `src/hooks/useFixedHeader.js`

**Issue identified**: Line 4 declares `const tableHeight = ref(500)` at module level. This means ALL components using `useFixedHeader` share the same `tableHeight` value. If two components use this hook, changing one affects the other.

```javascript
// Module-level — shared across ALL usages!
const tableHeight = ref(500);
export const useFixedHeader = (selector, headerHight = 50) => {
  // ...
  return { tableHeight, updateHeight };
```

**Rule compliance self-audit**:

| Rule | Compliance | Notes |
|---|---|---|

| 优先最小修改 | WOULD COMPLY | Move `ref(500)` inside the hook function |

## 3. Rule Effectiveness Assessment

### Rules that WOULD have been effective

| Rule | Effectiveness | Evidence |
|---|---|---|
| 修改前复述目标和影响范围 | HIGH | Forced me to state scope before coding — prevents scope creep |
| 优先最小修改 | HIGH | Natural constraint — one file, one fix |
| 禁止无关重构 | HIGH | I noticed the shared `tableHeight` issue but deliberately did NOT fix it because it's a separate concern |
| 异步函数必须处理错误 | HIGH | Clearly flagged `downloadFileAuto` as violating this rule |
| 不要自动新增依赖 | HIGH | No dependencies proposed for any task |
| 完成后说明验证和风险 | MEDIUM | Forces explicit risk statement, but AI may be vague |

### Rules that have gaps

| Rule | Gap | Recommendation |
|---|---|---|
| 行为变化必须验证 | No enforcement mechanism — AI can say "manual verification needed" and skip | Consider requiring specific test commands or page paths |
| 不要伪造测试结果 | Relies on AI honesty — no automated check | The `check` command helps, but can't verify runtime behavior |
| 需求不清先澄清 | AI may interpret "clear enough" differently than humans | Consider adding examples of what counts as "unclear" |

### Observations on AI behavior patterns

1. **Scope creep resistance**: The rules successfully prevented me from fixing the shared `tableHeight` issue when the task was about the debounce bug. Without the rule, I would have "helpfully" fixed both.

2. **Dependency discipline**: No new dependencies were proposed. The existing `@koi-design/vix-tools` `debounce` was reused.

3. **Error handling awareness**: The rule "异步函数必须处理错误" immediately flagged `downloadFileAuto`. Without it, I might have ignored the missing error handling.

4. **Self-assessment limitation**: I cannot objectively verify my own compliance. A human reviewer or automated hook would be more reliable.

## 4. Product Quality Observations

### What worked well

- `init --stack vue,typescript` correctly resolved to 7 assets (base + vue + typescript + 3 practice)
- `check` passed on first run — no false positives
- `list --assets` clearly shows included vs excluded assets with ●/○ markers
- Generated CLAUDE.md content is well-structured with category grouping
- Custom rule format is clear and documented in README

### What could improve

1. **Config version mismatch**: Config says `"version": "0.2.0"` but package is `0.2.1-beta.1`. The version in config should match the CLI version.

2. **No runtime verification**: Rules say "行为变化必须验证" but the tool only checks file-level consistency, not runtime behavior. A `br-rules verify` command that runs the project's test suite would close this gap.

3. **Custom rule TODO warning**: `br-rules add` generates `TODO: 在这里写规则内容` but `sync` doesn't warn about TODO content being rendered into target files.
