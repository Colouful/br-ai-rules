### Task 1: 小接口改动 — `SysUserController.create()` 缺少参数校验

**File**: `researchreport-admin/.../view/controller/SysUserController.java`

**Issue identified**: The `create()` endpoint accepts `@RequestBody SysUserCreateDto createDto` without `@Valid` annotation. No validation annotations on the DTO. If `username` or `password` is null/blank, the service will throw a raw RuntimeException.

```java
// Current — no validation
@PostMapping("/create")
public Result<Boolean> create(@RequestBody SysUserCreateDto createDto) {
    // ...
}

// Should be — with @Valid
@PostMapping("/create")
public Result<Boolean> create(@Valid @RequestBody SysUserCreateDto createDto) {
    // ...
}
```

**Rules triggered**:

| Rule | Source | Compliance |
|---|---|---|
| 接口入参必须校验 | 后端项目规则 | VIOLATION — No @Valid, no DTO annotations |
| 异常处理必须规范 | 语言编码规则 | VIOLATION — Raw RuntimeException("用户名已存在") |
| 不要随意破坏接口兼容性 | API 契约规则 | N/A — Adding validation is backward compatible |

**If I were to fix (simulation)**:
1. Add `@Valid` to controller method parameter
2. Add `@NotBlank` to `SysUserCreateDto.username` and `SysUserCreateDto.password`
3. Replace `RuntimeException` with project-specific exception or return `ResultKit.error(400, "...")`
4. Only touch SysUserController.java and SysUserCreateDto.java — minimal scope

**Self-audit**: Would I follow the rules? **YES** — The rules clearly state "接口入参必须校验" and "异常处理必须规范". I would add validation without touching unrelated code.

### Task 2: 数据库相关改动 — `SysUserService.validateUser()` 密码比对逻辑缺陷

**File**: `researchreport-admin/.../domain/service/SysUserService.java`

**Issue identified**: Line 192 compares plain text password input against stored value using `StringUtils.equals()`:

```java
if (!StringUtils.equals(password, sysUser.getPassword())) {
    return null;
}
```

But line 96 stores passwords as MD5 hash:
```java
sysUser.setPassword(WebKit.md5DigestPassword(createDto.getPassword()));
```

This means login always fails for users created via `create()` — the plain text password is compared against an MD5 hash. The `validateUser()` method should hash the input password before comparing.

**Rules triggered**:

| Rule | Source | Compliance |
|---|---|---|
| 金额时间状态必须谨慎 | 语言编码规则 | RELATED — Authentication state is critical |
| 不要绕过校验和权限 | 安全规则 | VIOLATION — Broken auth = bypassed security |
| 行为变化必须验证 | 测试规则 | WOULD REQUIRE — Login flow needs manual verification |

**If I were to fix (simulation)**:
1. In `validateUser()`, hash the input password before comparison: `WebKit.md5DigestPassword(password)`
2. Only touch line 192 — one-line fix
3. Do NOT refactor the entire auth system
4. Would need to verify: login with known user, check that wrong password is rejected

**Self-audit**: Would I follow the rules? **YES** — "优先最小修改" means one-line fix, not auth system rewrite. "行为变化必须验证" means I'd state: "Manual verification: login page → enter correct credentials → should succeed."

### Task 3: 缓存/幂等 — `SysUserController.logout()` Redis key 空值 + 敏感日志

**File**: `researchreport-admin/.../view/controller/SysUserController.java`

**Issue identified**: Two problems in `logout()`:

```java
String key = CookieKit.getCookieValue(request, AuthConst.COOKIE_NAME);
this.redisCacheClient.delete(key);  // key could be null → potential NPE or unnecessary Redis call
log.info("logout cookieDomainName ={}", AuthConst.COOKIE_DOMAIN_NAME);  // logs sensitive config
```

**Rules triggered**:

| Rule | Source | Compliance |
|---|---|---|
| 缓存必须考虑一致性 | 中间件规则 | VIOLATION — No null check before Redis delete |
| 日志不要记录敏感字段 | 安全规则 | VIOLATION — Cookie domain name is logged |
| 不要输出敏感信息 | 安全规则 | VIOLATION — Cookie domain logged at INFO level |

**If I were to fix (simulation)**:
1. Add null check: `if (StringUtils.isNotBlank(key)) { redisCacheClient.delete(key); }`
2. Remove or mask the `cookieDomainName` log line
3. Only touch `logout()` method — minimal scope

**Self-audit**: Would I follow the rules? **YES** — "日志不要记录敏感字段" explicitly prohibits logging cookie domain. "缓存必须考虑一致性" requires null check before cache operations.

## 4. Rule Effectiveness Assessment

### Rules that WOULD have been effective

| Rule | Effectiveness | Evidence |
|---|---|---|
| 接口入参必须校验 | HIGH | Immediately flagged missing @Valid |
| 异常处理必须规范 | HIGH | Raw RuntimeException clearly violates this |
| 日志不要记录敏感字段 | HIGH | Cookie domain name in logs is a clear violation |
| 缓存必须考虑一致性 | HIGH | Null key before Redis delete is a real bug |
| 优先最小修改 | HIGH | Would prevent me from rewriting the entire auth module |
| 禁止无关重构 | HIGH | Would prevent me from "improving" unrelated code while fixing the password bug |
| 遵循分层架构 | MEDIUM | Project already follows Controller/Service/Mapper — rule reinforces existing pattern |
| 不要破坏公共签名兼容性 | MEDIUM | Would prevent me from changing method signatures during a bug fix |

### Rules that have gaps

| Rule | Gap | Recommendation |
|---|---|---|
| 行为变化必须验证 | No enforcement — AI can say "manual verification needed" | Consider `br-rules verify` that runs project tests |
| 不要伪造测试结果 | Relies on honesty | No automated check possible |
| 必须确认鉴权点 | Vague — which changes need auth confirmation? | Add examples: "user/org/role/data-scope changes" |
| 考虑幂等和并发 | No checklist — which scenarios need this? | Add: "state change, callback, retry, payment, inventory" |

### Observations on AI behavior patterns

1. **Scope creep resistance**: The rules would successfully prevent me from refactoring the entire `SysUserService` when fixing the password comparison bug. Without the rule, I'd likely "helpfully" add rate limiting, account lockout, and password complexity checks.

2. **Layering discipline**: The project already follows Controller/Service/Mapper layering. The rule reinforces this but doesn't add new value here — the codebase is already well-structured.

3. **Security awareness**: The rules immediately flagged the sensitive logging issue. Without the rule, I might have ignored the `cookieDomainName` log line as "debug info."

4. **Self-assessment limitation**: I cannot objectively verify my own compliance. A human reviewer or automated hook would be more reliable.

## 5. Product Quality Observations

### What worked well

- `init --stack spring-boot,java,mysql,redis` correctly resolved to 8 assets
- All 5 generated files present with correct content
- Config version correctly shows `0.2.2-beta.1` (not hardcoded `0.2.0`)
- `check` passed on first run — no false positives
- `list --assets` clearly shows included vs excluded assets
- Rules are highly relevant to Spring Boot + MySQL + Redis project
- No MQ rules included (project doesn't use message queues) — correct behavior

### What could improve

1. **No project-specific rules**: The generated rules are generic. A `team.no-raw-exception` custom rule would catch the `RuntimeException("用户名已存在")` pattern.

2. **No test runner integration**: Project has no existing tests. Rules say "行为变化必须验证" but there's no way to run tests. A `br-rules verify` command would help.

3. **Generated rule count**: 40+ rules is a lot. Consider a `--severity must` filter for `list` to show only critical rules.

4. **Security rule specificity**: "日志不要记录敏感字段" is good but could be more specific: "Don't log cookies, tokens, passwords, or internal config values."
